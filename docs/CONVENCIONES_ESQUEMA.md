# CONVENCIONES DE ESQUEMA — Pie Firme (obligatorias para toda migración)

> **BASE COMPARTIDA (2026-10-26):** Pie Firme vive dentro del proyecto Supabase BITDATA (ref cruvkwgziksavetxtrvk), que aloja otro sistema en `comercio_cdmx`. Reglas: datos en el esquema **`piefirme`**, helpers de seguridad en **`piefirme_app`**; nada de Pie Firme en `public`, `auth` ni `storage` salvo buckets `pf-*` y políticas `pf_stg_*`; ningún trigger sobre `auth.users`; el cliente usa `db: { schema: 'piefirme' }` (VITE_DB_SCHEMA) y las funciones de servidor envían `Accept-Profile/Content-Profile: piefirme`; el registro de migraciones es `piefirme._rannix_migraciones`. Cuando abajo se lea `public.` o `app.`, entiéndase `piefirme.` y `piefirme_app.`. Sin extensiones (gen_random_uuid es nativo). `anon` solo tiene USAGE del esquema y EXECUTE de las RPC `portal_*`.

Base: `migraciones/001_base_organizacion_seguridad.sql` (organizaciones, sedes, cabinas, perfiles, rannix_staff, bitacora y el esquema `piefirme_app` con helpers). Lee ese archivo antes de escribir una migración.

1. **Numeración:** `migraciones/NNN_tema.sql`, una migración por tema, idempotente donde sea razonable; no edites las ya escritas de otro tema. Dependencias solo hacia números menores.
2. **Toda tabla de negocio** lleva `id uuid pk default gen_random_uuid()`, `organizacion_id uuid not null references organizaciones(id) on delete cascade`, `created_at`, `updated_at` (trigger `app.tocar_updated_at`) y, si es de una sede, `sede_id uuid references sedes(id)`. Índice por `(organizacion_id, …)`.
3. **RLS siempre:** `alter table … enable row level security` + políticas separadas select/insert/update/delete para `authenticated`. Plantilla: `using (organizacion_id = piefirme_app.org_id())`; escritura con `with check (organizacion_id = piefirme_app.org_id() and piefirme_app.org_activa() and piefirme_app.rol() in (…))`; lo que es por sede añade `and piefirme_app.puede_sede(sede_id)`. **Nunca `using (true)`**; nada para `anon` (el portal público usa funciones RPC `security definer` con rate limit y devuelven solo lo mínimo, p. ej. `piefirme.portal_*`).
4. **Roles:** `administrador`, `podologo`, `recepcion` (enum `rol_usuario`). El paciente NO tiene cuenta. Permisos exactos: `MATRIZ_ROLES.md` + `REGLAS_NEGOCIO.md`.
5. **Lectura por vistas `prp_*`** con `with (security_invoker = true)`; el frontend lee de vistas y escribe en tablas base (convención de IRP).
6. **Bitácora:** triggers `piefirme_app.auditar()` en tablas clínicas, financieras y de catálogo de precios; lecturas de expediente vía `piefirme.registrar_bitacora`.
7. **Dinero:** `numeric(14,2)`; precios con histórico en tabla `precios` (vigente_desde/hasta), nunca sobrescribir. **Fechas:** `timestamptz`; zona horaria de la clínica en `organizaciones.zona_horaria`.
8. **Funciones:** en `public` solo RPC que la app invoca (security invoker salvo portal); `revoke … from public, anon` y `grant execute … to authenticated`. Funciones `security definer` con `set search_path = public, pg_temp`.
9. **Storage:** buckets privados con URL firmada (`expedientes`, `fotos-clinicas`, `documentos`, `comprobantes`, `importaciones`); política por `organizacion_id` en el primer segmento de la ruta (`<organizacion_id>/…`).
10. **Nombres:** español, snake_case, singular→plural simple (`pacientes`, `citas`). Estados con `check (estado in (…))` tomados de `MODELO_ESTADOS.md`.
11. **No SQL de datos reales:** los datos de ejemplo van en `supabase/semillas/*.sql` (no en migraciones) y son sintéticos; Pie Clinic (5 sedes) es el ejemplo.
12. **Prueba:** cada migración debe pasar `node scripts/test-rls.mjs qa` cuando haya BD; mientras no la haya, valida la sintaxis leyendo con cuidado y, si hay `pg` y `pglite`/`postgres` local, aplícala en una BD local desechable.
